## 2. 충돌 해결 우선순위

새 요구사항과 기존 규칙이 충돌하면 다음 우선순위를 적용하세요.

### 오디오 분석 관련

다음 영역에서는 **이 프롬프트의 새 요구사항을 우선 적용**하세요.

* 비트 및 다운비트 추적
* 마디 구조 분석
* 프레이즈 및 섹션 경계 분석
* 하모닉/퍼커시브 분리
* 드럼, 베이스, 멜로디, 보컬 등 음악 레이어 추출
* 온셋, 오프셋, 지속 시간 및 음악 객체 추출
* 드래그 후보가 될 수 있는 지속음 분석
* 분석기 프로토콜과 DSP/ML 백엔드 구조

기존의 단순한 FFT, spectral flux, 자기상관 템포 추정, 온셋 중심 분석만으로는 부족합니다. 이 부분은 가능한 범위에서 새 구조로 교체하거나 확장하세요.

### 게임 노트 생성 관련

다음 영역에서는 **기존 프로젝트의 규칙과 동작을 우선 보존**하세요.

* 일반 노트의 종류와 의미
* 드래그 노트의 데이터 형식과 게임플레이 동작
* 드래그 경로 표현 방식
* 레인 수 및 좌표 체계
* 노트 충돌 처리
* 난이도 정책
* 손 배치 및 플레이 가능성 규칙
* 노트 렌더링과 판정에 필요한 속성
* SwiftData 저장 및 로딩 흐름

새 분석 결과는 기존 노트 생성 로직에 맞게 어댑트하세요. 기존 노트 시스템을 불필요하게 교체하거나 재설계하지 마세요.

단, 기존 노트 생성이 명백하게 무작위 삽입이나 음악과 무관한 규칙에 지나치게 의존한다면, 외부 인터페이스와 게임플레이 동작은 유지하면서 내부 입력 신호만 음악 분석 결과로 개선하세요.

* 드럼 트랜지언트
* 베이스 펄스
* 비지속성 멜로디 악센트
* 지속성 멜로디 또는 보컬

* 보컬 음절 어택
* 반복되는 리듬 모티프

기존 일반 노트와 드래그 노트의 최종 생성 방식, 경로 표현, 레인 규칙은 최대한 유지하세요.

새 시스템의 주된 역할은 기존 생성기에 다음과 같은 더 정확한 근거를 제공하는 것입니다.

* 어떤 시간에 노트를 생성할지

* 이벤트가 순간음인지 지속음인지
* 이벤트의 중요도와 신뢰도가 얼마인지
* 비트, 마디, 프레이즈 안에서 어떤 위치인지

# 난이도별 음악 레이어 선택

난이도가 높아질수록 무작위 노트를 추가하지 말고, 독립적인 음악 레이어를 더 많이 사용하세요.

기존 난이도별 노트 수, 속도, 플레이 가능성 규칙이 있다면 그대로 유지하면서 입력 후보의 음악적 품질을 개선하세요.

권장 레이어 정책:

* Easy

  * 다운비트
  * 강한 kick/snare
  * 주요 멜로디 앵커
  * 기존 정책이 허용하는 소수의 드래그

* Normal

  * 8분음표 싱코페이션
  * 베이스 펄스
  * 더 많은 멜로디 악센트
  * 기존 정책에 맞는 짧은 지속음 드래그 후보

* Hard

  * 독립적인 보조 레이어
  * 오프비트 퍼커션
  * 멜로디 세분화
  * 더 많은 고신뢰도 지속음 후보

* Hell

  * 멜로디, 베이스, 퍼커션, 보조 악센트 결합
  * 기존 NPS 및 충돌 규칙이 허용하는 범위에서 높은 중첩 밀도
  * 모든 추가 노트는 음악적 근거를 가져야 함

같은 온셋을 복제하거나 임의 패턴을 삽입해 밀도를 높이지 마세요.

# 드래그 후보 분석

드래그 노트의 최종 생성 규칙은 기존 로직을 우선 따르세요.

다만 기존 로직에 전달하는 드래그 후보는 반드시 지속되는 음악적 이벤트에서 생성하세요.

후보 소스:

* 지속되는 보컬 음
* 지속되는 보컬 음절
* 지속되는 리드 멜로디 음
* 긴 synth, pad, string 성분
* 리듬적으로 중요한 지속 베이스
* 연속성이 명확한 drum roll 또는 riser

후보에서 제외할 것:

* 단발성 kick/snare/hihat
* 무음
* 온셋 사이의 빈 공간
* 약한 노이즈 플로어
* 단순 온셋 간격
* 무작위 비율 할당

각 후보에 가능한 범위에서 다음 정보를 제공하세요.

* `onsetTime`
* `offsetTime`
* `duration`
* `sourceRole` 또는 `stemType`
* `meanEnergy`
* `sustainStability`
* `percussiveness`
* `pitchContour`
* `centroidContour`
* `voicingConfidence`
* `beatAlignedStart`
* `beatAlignedEnd`
* `sectionID`
* `phraseID`
* `importanceScore`
* `confidence`

드래그 적합도는 다음 원칙으로 계산하세요.

* 길고 안정적인 지속음일수록 점수 증가
* 보컬 또는 리드 멜로디일수록 점수 증가
* 연속적인 피치 윤곽선이나 명확한 글라이드가 있으면 점수 증가
* 지속되는 음절 또는 모음 정보가 있으면 점수 증가
* 퍼커시브하거나 노이즈가 많으면 점수 감소
* 해당 구간이 이미 혼잡하면 점수 감소

초기 최소 지속 시간:

* Easy: 1비트
* Normal: 1/2비트
* Hard/Hell: 연속성 신뢰도가 높을 경우 1/4비트

단, 이 값은 설정 가능해야 하며 기존 프로젝트의 드래그 최소 길이 규칙과 충돌하면 기존 플레이 규칙을 우선하세요.

# 드래그 경로 입력 정보

기존 드래그 경로 생성 알고리즘을 우선 유지하세요.

가능하다면 새 분석 계층에서 다음 정보를 제공하여 기존 경로 생성을 개선하세요.

* 안정된 피치: 동일 레인 또는 완만한 이동
* 상승/하강 피치: 방향성 있는 레인 이동
* 글라이드: 여러 앵커에 사용할 윤곽선 변화점
* 피치 신뢰도가 낮을 때: 보수적인 centroid/register 윤곽선
* 프레이즈 시작, 변화점, 종료 시점
* 비트 세분 위치

기존 경로 형식과 충돌하지 않는 범위에서 음악 윤곽선을 반영하세요.

기존 게임 규칙에서 무작위성 또는 시드 기반 경로 변화가 필요하다면 이를 제거하지 말고, 음악적 윤곽선을 중심으로 제한된 변형만 적용하세요.

# 타이밍

자기상관만 사용하는 템포 추정 대신 비트/다운비트 추적을 도입하세요.

기존 스냅 로직은 가능한 한 유지하되, 다음 정보를 추가로 사용하세요.

* beat confidence
* event confidence
* subdivision confidence
* syncopation plausibility

고신뢰도 이벤트가 음악적으로 타당한 오프그리드 위치에 있으면 기존 허용 오차 안에서 표현적 타이밍을 보존하세요.

그 외에는 기존 프로젝트에서 허용하는 가장 가까운 세분 위치에 스냅하세요.

권장 최대 세분:

* Easy: 1/2비트
* Normal: 1/4비트
* Hard/Hell: 1/8비트
* 근거가 강한 경우 triplet subdivision

기존 판정 시스템이 더 제한된 시간 해상도를 요구하면 기존 제한을 우선하세요.

# 레인 할당

기존 레인 할당 및 플레이 가능성 로직을 우선 유지하세요.

새 분석 결과는 레인 선택의 보조 신호로 사용하세요.

* 멜로디/보컬: 피치 윤곽선
* 베이스: 기존 규칙 내 낮은 음역 또는 외곽 성향
* snare: 안정적인 중앙 성향
* hihat/high percussion: 높은 음역 성향

단, 기존 손 교대, 레인 충돌, 패턴 가독성 규칙보다 음악적 음역 매핑을 우선하지 마세요.

# 구조 기반 생성

섹션과 프레이즈 정보를 기존 패턴 생성기에 전달하세요.

* 실제 음악이 존재하는 인트로를 임의로 비우지 않기
* 코러스에서 유사 모티프를 제어된 변형으로 재사용
* 반복 벌스는 같은 모티프 계열을 공유하되 전체 노트 스트림을 그대로 복제하지 않기
* 프레이즈 종료 정보를 드래그 종료 또는 해결 탭 후보로 활용

기존 패턴 재사용 규칙이 있다면 유지하면서 section/phrase 정보를 추가 입력으로 사용하세요.

# 결정론

동일한 오디오, 설정, 난이도, 시드에서는 동일한 결과가 생성되어야 합니다.

* 비결정적 컬렉션 순회에 의존하지 말 것
* 정렬 기준을 명시할 것
* 모든 랜덤 연산은 기존 seeded RNG 또는 하나의 명시적 seeded RNG를 사용할 것
* ML 분석 결과를 캐싱하거나 재현 가능하게 정규화할 것
* 분석기 변경 시 결과 버전을 기록할 것

# 데이터 모델

새 타입을 추가하기 전에 기존 타입으로 표현 가능한지 확인하세요.

필요한 경우에만 다음과 유사한 타입을 추가하세요.

* `BeatGrid`
* `BeatPosition`
* `SectionBoundary`
* `MusicalObject`
* `DrumEvent`
* `MelodyContour`
* `SustainCandidate`
* `AnalysisResult`
* `AnalyzerConfiguration`

기존 `Beatmap`, 노트 모델, 드래그 모델을 대체하지 마세요. 새 타입은 분석과 어댑테이션 계층에 집중하세요.

# 설정

모든 주요 임계값을 설정 객체에 모으세요.

최소한 다음 값을 설정 가능하게 하세요.

* onset confidence
* beat snap tolerance
* subdivision policy
* minimum sustain duration
* sustain stability threshold
* percussiveness rejection threshold
* layer별 중요도 가중치
* 난이도별 레이어 활성화
* 난이도별 NPS 한도
* drag candidate clutter penalty
* pitch/centroid contour smoothing
* section boundary sensitivity

하드코딩된 매직 넘버를 분산시키지 마세요.

기본값의 의미와 선택 근거를 코드 또는 문서에서 설명하세요.

# 테스트와 디버그

기존 테스트 구조를 유지하며 다음을 검증하세요.

* 비트/다운비트 타임라인
* 마디 위치
* 섹션 및 프레이즈 경계
* 드럼 이벤트 분류
* 멜로디 및 베이스 윤곽선
* 필터링 전 지속음 후보
* 난이도별 선택된 음악 레이어
* 음악 역할별 최종 노트 수
* 동일한 시드에서 동일한 결과가 나오는지
* 기존 SwiftData 저장/복원 호환성
* 기존 일반 노트 및 드래그 노트 동작이 유지되는지

한 곡에 대한 디버그 JSON 내보내기를 추가하세요.

JSON에는 최소한 다음을 포함하세요.

* analyzer/backend 정보
* configuration
* beats/downbeats
* sections/phrases
* extracted musical objects
* sustain candidates
* 선택 및 제외 사유
* 최종 노트의 source role
* 난이도별 통계

# 작업 절차

다음 순서로 진행하세요.

1. 관련 코드와 테스트를 조사하고 현재 구조를 요약하세요.
2. 기존 규칙과 새 요구사항의 충돌 지점을 식별하세요.
3. 변경하지 않을 기존 동작을 명시하세요.
4. 최소 침습적인 통합 아키텍처를 제안하세요.
5. 오디오 분석 계층부터 구현하세요.
6. 분석 결과를 기존 노트 생성기에 연결하는 어댑터를 구현하세요.
7. 기존 일반 노트와 드래그 노트 규칙을 유지한 상태에서 입력 후보 품질을 개선하세요.
8. 테스트와 디버그 출력을 추가하세요.
9. 빌드 및 테스트를 실행하고 실패를 수정하세요.
10. 변경 파일, 설계 결정, 호환성, 남은 한계를 정리하세요.

# 구현 시 필수 조건

* 실제 코드베이스를 기준으로 작업할 것
* 관련 파일 전체를 읽지 않고 추측하여 대체 구현하지 말 것
* 기존 노트 및 저장 모델을 불필요하게 재작성하지 말 것
* 오디오 분석은 기존 단순 방식보다 새 요구사항을 우선하여 개선할 것
* 노트 생성 규칙은 기존 게임의 동작과 플레이 감각을 우선 보존할 것
* 새 분석 결과를 기존 생성기에 맞게 변환하는 어댑터를 우선 고려할 것
* 노트 수 증가를 무작위 삽입이나 전역 임계값 하향으로 해결하지 말 것
* 드래그 후보를 단순 온셋 간격이나 무작위 확률로 만들지 말 것
* 기존 게임과 약하게 연결된 일반 반복 패턴을 새로 도입하지 말 것
* 빈 메서드, `fatalError`, 비동작 mock, `"implement later"`를 남기지 말 것
* 변경 후 프로젝트가 빌드되어야 할 것
* 기존 테스트와 새 테스트를 실행할 것
* 빌드 또는 테스트를 실행할 수 없다면 그 이유와 검증한 범위를 정확히 보고할 것

# 완료 기준

다음 조건을 만족해야 합니다.

* 새 오디오 분석 계층이 기존보다 명확한 비트, 마디, 섹션 및 음악 레이어 정보를 제공함
* 높은 난이도의 노트 증가가 주로 추가 음악 레이어 선택에서 발생함
* 드럼, 베이스, 멜로디가 독립적인 이벤트 스트림으로 추출됨
* 지속되는 보컬 또는 리드 음이 드래그 후보가 될 수 있음
* 반복 베이스 패턴이 멜로디와 독립적인 노트 후보를 생성함
* 드래그 후보가 지속성과 윤곽선 증거를 기반으로 함
* 기존 일반 노트와 드래그 노트의 게임플레이 규칙이 유지됨
* 기존 `Beatmap` 및 SwiftData 저장 흐름과 호환됨
* 동일한 입력과 시드에서 결과가 결정론적으로 재현됨
* 생성 결과가 비트, 마디, 프레이즈, 실제 오디오 이벤트와 연결됨
